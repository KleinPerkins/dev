# ADR 0001: Qualify private distribution for Sterling

## Context

Sterling's GitHub repository (ID 1439196929) is public, and its selected product distribution audience is private. Sterling PR #14 merged the block on signing and publication through the obsolete public route. Both repositories' public GitHub Release inventories were empty on November 20, 2026. Sterling release PR #5 was open.

Dev's predecessor (repository ID 1278387789) approved ADR 0018 and governed distribution PRD v1, requirements REQ-REPO-001 through REQ-REPO-020. The current Dev repository (ID 1459458379) retains ADR 0018 as historical provenance, while its current planning registry has no active distribution PRD, plan or qualified profile. Use a current authority record and preserve the predecessor's approvals and exact bytes.

Machine Monitor's private delivery component at revision `4f26c15527ef6912434e3953de6169aed8244e28` provides an implementation reference. Its Cloudflare Workers Free profile uses Worker-first routing, Cloudflare D1 for access and channel state, and authenticated delivery of bounded artifact parts. Its repository identifies the tool as source- and fixture-verified. PR #26 approved a revised CPU acceptance rule and allowed reassessment of the earlier run. Sterling needs evidence against its own live provider and product acceptance checks.

## Proposed decision

Carry the predecessor's provider-neutral distribution requirements forward into the current Dev authority for this migration. Preserve independent public-source and private-product choices. Bind Sterling's approved audience, product namespace, platform outputs, and profile version to repository ID 1439196929. Dev owns the approved binding and shared profile. Put reusable transport, grant lifecycle, artifact publication and conformance fixtures in one shared capability. Sterling owns its macOS build, signing, download and updater integration. Publish only approved nonsecret contract data. Maintain Machine Monitor's current deployment, client compatibility and distribution scope.

Qualify the Machine Monitor Workers Free design as the first candidate profile. Start with its pinned Worker-first, D1-backed private delivery implementation and its qualification/stable flow. Use a dedicated Sterling HTTPS origin, Worker, database, asset namespace, deployment state, product grants and updater key. Prove publisher isolation using effective provider permissions before activation. A shared provider account is eligible only if Sterling's publisher is isolated from Machine Monitor and other products. Require fresh evidence of Workers Free and the account's effective permissions before a provider mutation. Keep resources within the Free profile and require a new decision for any paid service, broad credential scope or custom domain.

Keep proprietary-source and binary entitlement decisions within each product's existing ownership. Distribution profile adoption does not itself change a product's license.

## Verification and delivery sequence

1. Adopt the requirement provenance and this profile decision in current Dev. Use the typed-plan acceptance procedure described by predecessor Dev ADR 0016, clauses C1–C4, for this migration in the current repository. Bind the plan to the exact accepted requirements and this ADR, validate the plan and sidecar, complete independent technical review, and obtain exact owner acceptance and operation-bound consent. This step uses the ordinary typed artifact transaction and grants no GSD runtime authoring or host activation authority. Verify effective ordinary PR delivery on current heads. Finish the Sterling migration independently of the separate new-repository intake rollout where neither shares a technical prerequisite.
2. Qualify a disposable non-product consumer before enabling Sterling publication. Verify allowed and revoked grants, anonymous and wrong-product denial, both channel permissions, no-store behavior, origin and preview access, HEAD/range handling, retained versions, effective provider role scope, Free quota/CPU capacity, provenance and integrity failures, interrupted publication, stale/concurrent promotion, and recovery. Measure on the actual provider using representative archive sizes. A failed check leaves the private publisher inactive.
3. Integrate the private client and publisher in Sterling. Keep its existing signed app identity `io.sterling.app`, Developer ID team, Sterling update key, universal build and macOS deployment target subject to their existing qualification. Ship only Sterling's approved outputs. Use a dedicated, importable Sterling recipient access file with the token held in non-synchronizing Keychain. Bind authenticated manifests and artifact parts to the configured HTTPS origin and channel. Validate complete archive integrity, code identity and version before installation. Keep update checks opt-in and automatic installation disabled. Feasibility and probe builds stay offline. Preserve the existing protected signing approval and hosted macOS CI, and retire the dormant public appcast and binary-upload path in the reviewed cutover. Align release-please with the private channel so version bookkeeping cannot create a public product release.
4. Verify merged source and required CI. With scoped provider and qualification-release authorization, deploy the isolated service, issue a short-lived qualification grant privately, and prove a Developer ID-signed, notarized and stapled clean install and an older-to-newer update. Verify failure behavior for revoked access and modified bytes, test the supported platform matrix, and record exact source, deployment and signed-byte evidence. Keep the stable channel empty until separate product release approval. Promote the verified immutable bytes through the qualified channel transition and verify recipient access and recovery behavior.

## Consequences

The migration is ready for implementation when the current Dev authority and requirement-bound execution plan are accepted. Provider bootstrap, distribution signing, stable promotion and product acceptance use their existing scoped authorization. Any missing profile binding, account isolation, exact-source checks, live access evidence or platform qualification keeps publication blocked.
