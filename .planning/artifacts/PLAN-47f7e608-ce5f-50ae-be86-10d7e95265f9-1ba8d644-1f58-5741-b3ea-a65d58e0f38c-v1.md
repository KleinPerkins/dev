## Capability and provider

Pin the public Machine Monitor source at revision `4f26c15527ef6912434e3953de6169aed8244e28`. The 22 credential-free provider and Worker tests passed against this revision on November 20, 2026, with Node 26.4.0. This is the synthetic reference baseline. Separate its product-specific identity, wire labels, browser copy, and macOS lifecycle from the shared transport and publisher primitives. Preserve its deployed protocol. Use a generic fixture consumer to prove that product and channel binding are enforced. Keep provider tooling independent of the audience decision and reject missing or stale central bindings.

Before either disposable provisioning or any Sterling provider mutation, obtain scoped authorization for the exact resource set and operations. Read the actual account's Workers Free status with account ID and a fresh owner dashboard observation within the profile's one-hour window. Verify the selected tool pins, the role and deployment permission inventory, remaining Free quotas and existing attachments. An unavailable observation or mismatch blocks mutation. Make one scoped bootstrap operation for the approved resources. Use separate credentials scoped to routine deployment, publication and recipient grants. Paid services, broader authority and a custom domain require a new owner decision.

Use disposable sibling resources for isolation tests. Require the scoped publisher to update and read back only its own fixture Worker, assets, D1 records, channel pointers and grants. Require denial of sibling Worker/version writes, sibling database queries and binding changes, sibling asset access and alternate channel or product writes. Verify unchanged synthetic sibling readback after negative cases. Check Worker-editor deployment authority and direct D1 authority separately. Document provider administration as residual privileged access. If account sharing cannot enforce cross-product isolation, qualify an isolated account through a separately approved bootstrap.

Run the approved nonsecret projection on a clean public-consumer checkout without credentials for the private predecessor. It must validate the repository identity, source/audience, profile version, output/channel scope and currency. Change each bound field in turn, remove the projection, roll back the profile version and supply an unqualified revision. Every invalid plan must fail before packaging, deployment or publication. Independently verify actual provider rights using scoped fixture credentials. Record which checks are advisory, which stop activation locally, which are enforced by the live service, and which owner/admin powers remain.

Provider acceptance records exact configuration and all active versions, including any zero-percent version. Use unconditional Worker-first routing, no static fallback, disabled version URLs and a single approved origin. Use independently checked fixture grants to verify anonymous, expired, revoked, wrong-product and wrong-channel outcomes on manifests, descriptors and bytes. Check HEAD/range/cache behavior, API consistency during revocation, asset readback, interruption and bounded first-release failure. Attempt to republish an existing fixture version with changed archive bytes and with altered signed metadata. Both requests must fail. Read back and hash the original descriptor and all retained parts, and verify that the stable channel pointer is unchanged. Demonstrate that retrying the exact original publication is idempotent and that a stale or concurrent request cannot replace an advanced pointer. Verify compatible recovery without decreasing a client's accepted build.

Before the live test, freeze a workload matrix using the larger of the projected first-install ZIP and update ZIP, a second fixture at the largest approved archive size, and the bounded recipient population. Count manifest, descriptor, part and HEAD requests plus valid and denied cases, revocation and parallel downloads. Test observed Free CPU P99 below 10 ms, P99.9 below 20 ms and zero execution-limit errors, using the Machine Monitor acceptance successor as the candidate rule. Use the currently documented provider quotas and a versioned budget that reserves at least 20% headroom after the approved peak daily operation and retained rollback assets are included. Record full-window request timings, CPU, memory, request and D1 units, and asset count. Qualify only when every target and platform limit passes.

Enroll, use, replace, revoke and recover a disposable recipient grant for each applicable channel. Replacement sends a new credential through the approved private owner channel and expires or revokes the old one. Recovery starts with a new grant and removes any lost token's future access. After acknowledged revocation, replay manifest, descriptor, piece GET and HEAD requests through the tested origins and caches. Every request started after the acknowledgement must deny. Record the first denial from each route within five seconds of the acknowledgement. Measure separately for already in-flight responses and previously downloaded bytes. Verify no publisher credential in client package, browser assets, manifests or logs.

## Sterling adapter

Read signed distribution configuration for the fixed origin, channel, update key and app/team identity. Keep access-file import explicit, validate the entire file, and store the grant in non-synchronizing Keychain. Use authenticated same-origin requests without redirect or public fallback. Verify manifest identity, monotonic build, exact ordered parts, full length/hash and Ed25519 signature. Before installer handoff, validate the reconstructed app's exact bundle identifier, Developer ID team, hardened and valid code signature, Gatekeeper result and monotonic version/build. Include correctly delivered but wrong-bundle, wrong-team, wrong-version and invalid-code-signature fixtures. Each must leave the installed app intact. Evaluate reusing the Machine Monitor one-session local Sparkle bridge with validated local bytes while keeping Sterling's own lifecycle and user-confirmed install. Treat cancellation, revoked access, interruption, invalid bytes and concurrent checks as terminating without installing or altering the last known working app. Preserve passive behavior and Hide/Pause priority.

Replace the public appcast build setting and public upload dispatch. Review release-please and GitHub credential scopes together so the old release route cannot publish on retry at current source. Preserve the owner-protected signing environment. Use Developer ID signing, timestamping, Apple notarization/stapling, Gatekeeper and the Sterling Sparkle signing key. Run complete Swift and delivery tests, repository checks and macOS CI. Confirm the current Dev classification and live native GitHub/App admission at Sterling's exact head. Use a source audit to confirm the frozen approved PRD/specification bytes, dependency boundaries and one SterlingCore state owner. Run reducer/interaction regression coverage for forgiving absence and owned gestures, plus probe and physical observations appropriate to passive hit-testing and Hide/Pause. Assert that local builds and probes do not open an updater or network session, that default/manual and opt-in automatic checks are preserved, and that background checks cannot silently install. Record the existing install path or its absence before any cutover. If earlier signed copies exist, prove that the chosen update or documented manual migration preserves the installed app, applicable state and rollback target. No public-path removal, data deletion or deployment occurs outside the accepted transition. Cover malformed/missing configuration, revoked access and tamper failure, and exercise the normal build/update entry points.

Confirm install and update on the agreed supported OS/architecture matrix. Stage exact current-main builds in an owner-only qualification channel using ephemeral scoped access. Keep the stable channel empty until product release approval. Any failure before promotion preserves the previous stable pointer, or empty stable for the first release. If stable readback fails, use the verified recovery transition appropriate to the accepted client build ordering, or stop serving stable until a higher-build corrected release is qualified.
