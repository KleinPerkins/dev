# Doc-Warden v2 current continuation requirements

## Problem, users and value

The operator and authoring agents need one reliable account of agreed product behavior, requirements, design, decisions, plans, progress and completion evidence. Separate documents and recovered sessions can otherwise disagree, silently change accepted intent or mistake preserved work for completed implementation.

Continue the accepted in-boundary Doc-Warden v2 product in the current Dev repository. Preserve the full retained governance scope. Add the owner's explicit requirement that Save-Game integration is mandatory for governed authoring continuity. The initial continuation unit prepares current authority documents and a grounded implementation-gap assessment; it does not claim the whole roadmap is already delivered.

## Current behavior and target behavior

Current Dev contains v2 schemas, typed artifact publication, rigor/roadmap/reconciliation machinery and an adapter whose source treats Save-Game as optional. Ordinary semantic document publication is distinct from central GSD authoring, whose current successor plan binding remains intentionally unbound. Existing code and historical tests require a fresh requirement-by-requirement gap assessment before choosing the next implementation unit.

The target product connects product intent to design, technical decisions, implementation plans and proof; keeps approved meanings stable through explicit successor versions; reports current blockers and dependencies; and provides required private Save-Game continuity without transferring ownership of checkpoints or overriding live authority.

## Retained scope provenance

The predecessor plan's governance requirements remain the source of product scope: authority/lifecycle/graph/PRD/defects/rigor/UI/roadmap, authoring continuity, dependencies, operator experience and views, triggers/new-repo/migration/receipt/privacy/compatibility/path/policy correctness. This table groups them into current requirements rather than silently removing capabilities. The historical autonomous-execution/security rows stay deferred; legacy delivery and runtime qualification assertions do not carry forward as current evidence.

The one selected product amendment is required Save-Game integration, governed prospectively by the current Save-Game continuity ADR. Frozen optionality wording remains historical. No implementation or native client qualification is inferred from adopting this amendment.

## Journeys and failure recovery

A feature starts from approved intent, gains design when applicable, then a specification/decision/plan bound to its requirements. Changes to accepted assumptions flag affected work for refinement. Progress and generated views evolve separately from accepted plan bytes. Completion names actual verification and applicable user acceptance evidence.

An authoring handoff identifies live authority, writes a private supported Save-Game checkpoint/index and records only the valid closed pointer. A later resume reconciles the checkpoint against live source. Capability failure or conflicting source blocks the continuity-dependent operation without overwriting the last valid checkpoint or claiming success. Repeated requests reuse supported identity and recovery behavior; exact retry/idempotency ownership is checked during the source gap assessment.

## Non-goals and constraints

Autonomous coding or cross-phase execution, security-grade sandbox/consent/tamper guarantees, Git delivery ownership, worktree creation, a generic release orchestrator and new MCP runtime remain outside this product scope. AWA, Save-Game, local-jobs, repository CI/App and product release owners retain their responsibilities.

This continuation does not authorize installation, adoption, real private checkpoint invocation, scheduling, fleet migration, old-source replay, cleanup, PAC restart, code implementation or product release. Those operations require their precise later authority. Existing native project roots, original histories and installed runtime pins remain intact.

## Dependencies, risks and success measures

Dependencies are the current Dev typed publisher and owner governance; the exact qualified GSD authoring binding where used; the independently owned Save-Game contract; and each affected repository's current source-delivery path. Save-Game installed exposure, adoption and native client invocation are observed per host/client, never inferred from source or another machine.

Success requires complete requirement coverage, exact authority bindings, passing relevant source checks, independent technical review, explicit acceptance and honest gap reporting. Installation, native authoring/client qualification, full product completion and release require their separate evidence. Initial authority preparation succeeds only when current accepted records and a bounded next-unit decision are delivered; a reviewed private proposal alone is not that result.

## Open implementation decisions

The gap assessment must resolve the exact continuity event matrix, integration surface, retry semantics and destination-native acceptance checks against live owner code. It must identify supported behavior and missing work without expanding scope or claiming Save-Game's unimplemented rollback operations. Material architecture or capability-owner changes return as concrete decisions before dependent implementation.
