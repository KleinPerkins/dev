# Governed repository visibility and distribution requirements

## Purpose

Use independent source visibility and product distribution decisions under the current Dev operating model. Preserve the twenty original requirement IDs, statements, and acceptance conditions below. Sterling (GitHub repository ID 1439196929) is the first migration with public source and private product distribution. The current Dev ADR and an accepted requirement-bound plan govern its implementation.

This carries forward requirement definitions from the approved predecessor PRD version 1 (repository ID 1278387789, source revision `24bdc69e3cf0ecb859f77db330d6019166f14a49`, artifact SHA-256 `5840793c4c846ad301820d8c5c45ec01314238bb28abead596deeb169d2c7fff`). The predecessor approval remains evidence of the historical decision. The current record requires its own acceptance.

## Requirements

| ID | Requirement | Acceptance |
|---|---|---|
| REQ-REPO-001 | Resolve source visibility explicitly as public or private before creation begins. | Missing or invalid source intent causes no directory, Git, remote, commit or credential creation. Existing explicit operator direction is reused. |
| REQ-REPO-002 | Resolve product distribution independently as public, private or explicit none before creation begins. | Every allowed source/audience combination is supported; missing intent is never inferred from source visibility or a default. None refuses product publication. |
| REQ-REPO-003 | Apply intake to all supported creation entry paths. | Agent, interactive/noninteractive CLI, product/capability, legacy, no-push and resume paths use the same validation. Source flags do not authorize distribution. |
| REQ-REPO-004 | Preserve exact intent and immutable identity across creation and resume. | Pre-remote state binds a planned repository key; post-remote observation binds the provider ID. Interrupted operations neither recreate/delete remotes nor invent missing decisions. |
| REQ-REPO-005 | Keep approved intent separate from observed state and repository-local configuration. | The central approved record owns audience permission. Local edits, names, paths, renames or current provider visibility cannot broaden it. |
| REQ-REPO-006 | Reuse one central distribution standard and capability through isolated umbrella overlays. | Consumers share contracts, qualification and lifecycle tooling while retaining only product configuration/adapters. Cross-umbrella enrollment grants no mutation authority. |
| REQ-REPO-007 | Keep requirements provider-neutral and qualify tools against them. | No updater, identity provider, registry, host, CI engine or custom service is prescribed. A generic fixture consumer qualifies before Sterling-specific integration. |
| REQ-REPO-008 | Make approved nonsecret bindings usable by public consumers. | Public consumers validate policy identity/version/currency without broad access to private dev contents, other repository records or credentials. |
| REQ-REPO-009 | Authenticate all private distribution surfaces and underlying storage. | Actual-service tests cover manifests/catalogs, downloads/packages/images, direct origins, redirects, caches, HEAD and ranges. Unlisted URLs or CORS alone cannot qualify. |
| REQ-REPO-010 | Provide scoped recipient enrollment, replacement, revocation and recovery. | Qualify the revocation window including token/cache lifetime, appropriate credential custody and cross-project/channel isolation. No product contains publisher credentials. |
| REQ-REPO-011 | Verify producer identity, artifact integrity and exact output provenance. | Use appropriate product/platform/package trust and bind version, source, output inventory and digests. Private-source/public distribution exposes only designated outputs. |
| REQ-REPO-012 | Enforce immutable versions and qualified promotion/recovery. | Reject changed published bytes and stale/concurrent promotions. Exercise interrupted uploads, failed final checks, first-version failure and recovery of the known working target. |
| REQ-REPO-013 | Refuse unapproved publication at the effective credential/provider boundary. | Bind the current approved project, audience, policy/profile, source and output scope. Missing/stale/unqualified configuration never falls back to public delivery. |
| REQ-REPO-014 | Preserve independent source CI, merge authority and governance boundaries. | No audience choice grants runner exceptions, changes other repositories' lanes, expands controller command execution or turns doc-warden into a release orchestrator. |
| REQ-REPO-015 | Report enforcement strength and drift accurately. | Creation/activation gates, provider authority and advisory doctor observations are distinguished. Owner/admin bypass capability and broad provider permissions remain explicit limits. |
| REQ-REPO-016 | Migrate existing repositories through explicit decisions and recoverable cutovers. | Read-only inventory never infers approval or mutates visibility/releases. Preserve current source/CI and installed client paths except for approved changes; public bytes are not claimed to become retroactively secret. |
| REQ-REPO-017 | Contain Sterling's existing public publication path before a new binary release. | Prepare/sign/publish invocations and release retries cannot upload public binaries/feeds or fall back to public URLs while private delivery is unqualified. |
| REQ-REPO-018 | Migrate Sterling as a consumer of the central standard. | Bind repository ID 1439196929 and public-source/private-distribution choices, reconcile its existing native CI classification, use qualified shared tooling and retain product-only macOS integration. |
| REQ-REPO-019 | Preserve Sterling's approved product and runtime boundaries. | Frozen PRD/specification bytes, one simulation owner, passive input, forgiving care, Hide/Pause precedence, local/probe networking isolation, opt-in checks and disabled silent installation remain intact. |
| REQ-REPO-020 | Prove source delivery and actual private distribution separately. | Required local/hosted current-head checks and verified merge establish source delivery. Actual service access, a clean signed install and a later installed update require separate evidence and existing product/release authorization. |

## Rollout boundary

Prioritize the shared profile and Sterling migration under REQ-REPO-005–020. REQ-REPO-001–004 retain their original meaning and remain open for the separate repository-intake rollout. REQ-REPO-017 has merged Sterling containment evidence and must remain satisfied throughout cutover. Profile qualification, repository binding, protected source delivery, live provider access, signed installation and an installed update require the evidence specified above. The product retains its existing release and acceptance gates.
